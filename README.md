# AISI

Sparse encoding (SAE-based) detection of adversarially trained steganographic encoding in LLM chain-of-thought reasoning.

## Goal

Detect whether a model's chain-of-thought (CoT) contains steganographically encoded information — i.e. content hidden in reasoning text by a model that has been adversarially trained to encode signals covertly. Approach: train sparse autoencoders (SAEs) on CoT activations and use the resulting sparse feature space to surface encoding patterns that aren't visible from the raw text alone. The SAE detection pipeline itself (`src/sae/`, `src/models/`, `src/eval/`) hasn't been started yet — every experiment below is upstream work: getting a model that actually exhibits (or is being pushed toward) steganographic encoding, which the SAE work will need as its subject.

## Paper

The LaTeX source and compiled PDF of the ICLR submission live in Overleaf, **not in this repository**. This repo is the experiment code, evidence, and documentation the paper draws on. `analysis_paper_audit/` contains a prior audit tying paper claims to repo artifacts (see `analysis_paper_audit/AUDIT_REPORT.md`); treat it as a cross-reference, not the source of truth for either side.

## Running an experiment

Early stages (through roughly `06_stage4_coinflip_merge`) are self-contained Colab
notebooks under `experiments/<NN_stage>/notebooks/`, generated by a matching
`experiments/<NN_stage>/data_generation/build_*.py` builder script. To reproduce or
modify a notebook, edit its builder script and re-run it locally (no GPU needed for
the build step itself), then run the regenerated `.ipynb` on a Colab L4.

**Before running any builder script that writes to an existing notebook path**: it
will refuse to silently overwrite a notebook that already has executed output cells,
and will tell you what to do instead. This exists because exactly that accident
happened once during the 2026-08-22 reorganization — see the note in
`experiments/04_stability_investigation/README.md`.

Later stages (`07_positive_signal_annealed_reward` onward) instead run as standalone
scripts directly on a GPU instance (AWS EC2, g5.xlarge), with evidence retrieved and
hash-verified into that stage's own `aws_runs/` (or, for stages recovered after the
fact, `aws_recovered/`) directory. Each such stage's `README.md`/`design.md` states
its exact launch command and dependencies.

## Experiment history

Chronological, one folder per stage. Each stage's `README.md` follows the same
template where present: what we tried, why, key steps/iterations, final result, what
it meant for the next step (see Part A's documentation-hygiene notes for the three
stages that do not yet have one). Superseded/one-off material is in
[`experiments/archive/`](experiments/archive/), out of the main sequence.

| # | Experiment | Question it answers | Result |
|---|---|---|---|
| [00](experiments/00_infrastructure/) | Infrastructure | — | reused components (data gen, reward, dynamic sampling, safeguards) |
| [01](experiments/01_direct_rl_coinflip/) | Direct RL on Coin Flip | **Discovery**: does RL under a lexical penalty alone induce non-literal encoding? | negative — 3,200+ rollouts, zero verified encodings |
| [02](experiments/02_demonstration_seeding_single_domain/) | Single-domain seeding (latch) | **Adoption**: can a model adopt a given non-literal code from single-domain demonstration? | checkpoint accepted for its own task, zero cross-domain transfer |
| [03](experiments/03_demonstration_seeding_multi_domain/) | Multi-domain seeding (fan+valve→lamp) | **Adoption**: does training across ≥2 domains force the code to generalize as an abstraction? | executes a given code (86-89%), fails to invent one (10%) |
| [04](experiments/04_stability_investigation/) | Checkpoint-500 KL instability | Infrastructure: why does resuming checkpoint 500 for further GRPO reproducibly blow up, and how is it fixed? | mechanism found (policy/reference mismatch), mitigation built and later validated |
| [05](experiments/05_self_bootstrapping/) | Self-bootstrapping | **Adoption**: can the model bootstrap its own encoded-trajectory dataset rather than being handed one? | the intended arbitrary-only dataset was formally closed out as not viable (qualifying pool empty after a classifier fix); proceeded with Dataset B, a domain-leaking fallback, which fed into `06`'s merge |
| [06](experiments/06_stage4_coinflip_merge/) | Stage-4 coinflip merge | **Adoption**: does merging checkpoint 500 with the Dataset-B seeded-invention adapter induce genuine invention on Coin Flip itself? | negative — zero genuine invention |
| [07](experiments/07_positive_signal_annealed_reward/) | Positive-signal annealed reward | Reward-shaping: does a differently-shaped reward (continuous partial credit, annealed pressure) surface invention that pressure alone couldn't? | negative — 0 non-literal rollouts ever produced for the reward to act on |
| [08](experiments/08_load_bearing_and_exploration_audit/) | Load-bearing & exploration audit | Foundational: does the task structurally require encoded state, and does higher-temperature sampling alone ever produce a non-literal attempt? | motivates the direct-demonstration approach in 09 |
| [09](experiments/09_direct_indomain_synthetic_bridge/) | Direct in-domain synthetic bridge | **Adoption**: does directly demonstrating valid encoded trajectories (SFT injection) bridge the model into non-literal territory it never spontaneously explored? | see stage README/design.md for the full Step 0-14b arc |
| [09b](experiments/09b_model_scale_ablation/) | Model-scale ablation | Does the bridge result replicate at larger model scale (7B)? | see `design.md` (no README.md yet — see Part A finding) |
| [09c](experiments/09c_sft_diagnostic/) | SFT representational-capacity diagnostic | Separate from RL adoption: can the model represent/imitate the code via direct SFT at all? | see `design.md` (no README.md yet — see Part A finding) |
| [09d](experiments/09d_sft_seeded_adversarial_rl/) | SFT-seeded adversarial RL | Full investigation arc: does SFT-seeding + adversarial RL pressure produce genuinely causally load-bearing (steganographic) encoding? | negative — no checkpoint from Stages 9/9b/9c/9d qualifies (see `design.md`; no README.md yet — see Part A finding) |
| [09e](experiments/09e_same_different_llama/) | Same/Different task redesign, Llama-3-8B | **The redesigned Llama causal test**: does a different model family + an answer-format redesign (the code word itself is the answer, no decode-back step) produce genuinely causally load-bearing encoding? | **yes** — bidirectional intervention: 42/42 pre-RL, 167/168 post-RL across 4 seeds (concealment against a reader left untested here — see 11) |
| [10](experiments/10_literal_cot_adversarial/) | Literal-CoT adversarial pressure | **The literal-CoT adversarial test**: can adversarial lexical-penalty pressure induce non-literal encoding when applied to a policy already confirmed 100% literal (unlike every prior lexical-penalty run in this project)? | negative — 100% penalty engagement on every rollout, still 0/0 non-literal, MAIN statistically indistinguishable from BASELINE |
| [11](experiments/11_concealment_tests/) | Concealment tests | **The two concealment probes**, applied to 09e's causally-load-bearing code: (1) semantic monitor — does the code conceal state from a reader who doesn't know the mapping? (2) paraphrase defense — does the causal role survive the trace being reworded? | (1) mixed — clustering is trivially recoverable (mathematically guaranteed for this code), but a real-world-label judge (`semantic_monitor_v2`) scores no better than an uninformed heuristic; (2) no — 100% of paraphrased traces preserve both the code sequence and the model's correct causal continuation |

Full chronological detail, including everything not compressed into the per-stage
summaries, is in [`logs/development_log.md`](logs/development_log.md) — the source of
truth every `experiments/*/README.md` above was written from.
